## Ошибки и несостыковки

### P1. Большая группа теряет приказ после 64-го юнита — подтверждено

`net/controls.ts: orderGroup` делит группу по 64. `net/session.ts: command/flushOrders` объединяет части с одинаковыми действием и целью обратно в один пакет. `engine/game.ts: execNetCommand/units` использует `list.slice(0,64)`. Воспроизведение: группа 100 → один исходящий пакет с 100 ID → движок применяет только первые 64. Остальные остаются без приказа.

Исправлять пакетирование при финальной отправке: максимум 64 ID на команду после объединения. Не просто расширять приём без проверки лимита размера/команд сервера. Регрессия должна пройти путь installNetControls → NetSession → execNet, проверить приказ у всех 100/204 юнитов и одинаковые хеши двух зрителей.

### P1. Массовая команда без цели теряет юнитов из-за лимита сервера — подтверждены пакетирование и лимит

`ui/command.ts:299–304` вызывает `unitCommand` для каждого выбранного юнита. Сетевой controls шлёт отдельный `act` с одним ID. NetSession объединяет только `order`, не `act`. Воспроизведение: 50 приказов GUARD → 50 сообщений. `server/dune-net.mjs` принимает максимум 24 команды одного игрока за ход и молча отбрасывает остальные. Дополнительно общий бюджет 80 сообщений/сек.

Нужно объединять совместимые групповые `act`, делить по 64 после объединения. Не ломать порядок приказов одного UI-события и смену действий. Добавить тест с реальным сервером/полной цепочкой: вся группа 50+ реагирует, никто не теряется из-за лимита.

### P1. Неполная сетевая команда может уронить обработку хода — подтверждено исключение

`game.execNet(1,{k:'order',a:1,p:1000})` выбрасывает `TypeError: Cannot read properties of undefined (reading 'slice')`. Сервер проверяет лишь object/k/размер и принимает такую форму `cmd`; поэтому некорректный или несовместимый клиент может разослать её всем. На живых игроках не воспроизводили — только изолированно.

Добавить проверку схемы команд на сервере и защиту исполнения на клиенте: типы/диапазоны чисел, массивы ID, размер, допустимые действия; серверную `left` оставить недоступной клиентам. Не полагаться на TS-типы входящего JSON. Тест: плохой пакет отвергается, следующий корректный ход продолжает выполняться, оба клиента совпадают.

### P2. Готовая постройка может перехватывать управление — наблюдалось, нужен изолированный тест

В живом матче после выделения двух квадроциклов завершился космопорт, меню переключилось обратно на двор и режим размещения. Не выдавать точную первопричину за доказанную: пользователь также работал в видимой вкладке, поэтому нужен отдельный сценарий без постороннего ввода.

Проверить `main.ts:1010–1020`, `completedConstructionYard`, `queuedPlacementYard`, `readyYardAt`, `hoveredReadyYard` и выбор здания. `queuedPlacementYard` устанавливается при размещении предыдущей постройки. Требование пользователя сохранить: готовое здание автоматически на курсоре при работе со двором, следующие из очереди тоже; ПКМ отменяет. Но стройка не должна забирать выделение у армии или режим наведения в бою. Протестировать оба поведения.

### P2. Радар фактически не управляет деталями мини-карты — подтверждено

Подробная мини-карта работает с начала матча без радара. `houseUpdateRadarState` вычисляет `radarActivated` по наличию OUTPOST и энергии; визуальный код мини-карты этот флаг не использует. В main отображение связано только с `prefs.radar`.

**Пользователь явно поручил сделать как в оригинале.** Для Sega подробный радар требует аванпост и питание, при дефиците энергии отключается. Связь с технологиями тоже должна соответствовать игре. Первоисточник: подсказки Virgin/Westwood для Genesis, https://www.ledmeister.com/dunehint.htm (A2, B2). Точный упрощённый вид без радара уточнить по ROM/оригиналу, не переносить автоматически режим DOS. Не открывать весь туман или врагов при включении радара.

Смотреть `engine/house.ts:212+`, `engine/structure.ts`, `ui/minimap.ts`, `main.ts` (prefs.radar).
