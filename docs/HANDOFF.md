# Передача проекта: карта, состояние, что дальше

Документ для агента, который продолжит работу. Сначала прочитай его целиком, затем `README.md`:
там подробности формата ROM и устройства движка.

## Цель и пожелания владельца

- Ремейк Sega Mega Drive «Dune: The Battle for Arrakis» (у владельца русская версия от «Шедевра»)
  в браузере. Это **свой движок, а не эмулятор**.
- Механика и поведение должны быть **точно как в оригинале**: «всё смотри по оригиналу, как делается».
  Если не уверен, проверяй в эмуляторе и в коде ROM (см. «Инструменты»). Эффекты (взрывы, дым)
  можно делать своими.
- Управление:
  - геймпад как в оригинале: стрелки — курсор, 1/2/3 — A/B/C, Enter — Start;
  - режим «Мышь» (M) — как в Red Alert, стрелки в нём только двигают карту.
- Графику владелец будет перерисовывать. Для этого есть экспорт и импорт набора PNG («Ресурсы» → ZIP).
- Уточнение по HD-зданиям: сохранять оригинальные силуэт, пропорции и расположение частей из ROM,
  улучшать только прорисовку. Свободный редизайн не подходит. Исключение — уже одобренный двор с краном:
  его владелец просил оставить. Площадки и фон тоже сохранять, не делать прозрачные дыры.
- Следующий этап HD: владелец попросил начать с заставки и меню, также улучшить буквы.
  Картинки должны быть широкими (16:9), края дорисовывать, объекты не растягивать. Надписи
  рисовать гладко в нативном разрешении, а не увеличивать растровый шрифт 320×224.
- Тексты русские. Пароли и коды — как в оригинале.
- Игра только для личного использования. **Сам ROM в репозиторий не кладём** (`.gitignore`: `/rom/`,
  `*.gen`, `*.bin`, `/out/`, `third_party/`).
- **С 2026-10-19 (решение владельца):** правится локальная рабочая папка
  `C:\Users\Admin\Downloads\dune-remaster-main\dune-remaster-main` (в ней нет `.git`), а GitHub
  (`Angellis2000/dune-remaster`, публичный) — её полная копия: код, медиа `web/public`, `scratch/`,
  `hd-vehicles/`, модели piper, журналы. Не копируются только ROM, `node_modules`, `web/dist`, кэши.
  Синхронизация: копия в git-клоне `D:\DUNA 2` (robocopy с этими исключениями), проверки
  (`npx tsc --noEmit -p web`, `npm test`, `npx vite build`), коммит в `main` и `git push origin main`.
- Владелец пишет коротко и по-русски, отвечать тоже по-русски.
- Владелец играет в опубликованной странице (Artifact `dune-remaster`). После сборки страницу
  обновляют: собранный `web/dist/assets/index-*.js` публикуется рядом с HTML-обёрткой, которая

## Как запустить

```
cd web && npm install && npx vite build && npx vite preview --port 4173
# открыть http://localhost:4173/ и выбрать ROM (rom/dune_usa.gen)
# http://localhost:4173/?debug — сразу миссия; в window.dune: world, view, G, sprites, mentat, endPicture,
#   scoreScreen, frontend, sound, tutorial, finale (у экранов есть stepFrames(n) для автотестов)
npx tsc --noEmit -p web            # проверка типов (strict, noFallthroughCasesInSwitch)
node --experimental-transform-types tools/sim/build_time.ts   # движок без браузера
OUT=/tmp node tools/browser/hud.mjs rom/dune_usa.gen  # Playwright, нужен preview на :4173
# build_place.mjs устарел: ждёт правое меню с геймпада и view.readyStructures, которых больше нет
```

В подготовленной облачной среде Playwright стоит в `/opt/codex/cua_node/lib/node_modules/playwright`,
Chromium — `/usr/bin/chromium`. Старые браузерные скрипты используют пути прежней среды:
запускай их из корня через `node /workspace/.dune-tools/run-browser.mjs tools/browser/hud.mjs rom/dune_usa.gen`.
Сервер разработки — `cd web && npm run dev -- --host 127.0.0.1 --port 5173 --strictPort`;
проверки старых браузерных скриптов используют preview на 4173. Графического Chrome в этой среде нет:
проверки запускаются в фоновом Chromium, пользователю можно показывать свежие скриншоты.
Скрипты в `tools/browser/*.mjs` загружают ROM через `#rom-file`, жмут клавиши и сохраняют
снимки в `$OUT`. Скрипты в `tools/sim/*.ts` гоняют движок в Node; пути к ROM в них абсолютные
(`/home/user/dune-remaster/...`), при необходимости поправь.

`rom/dune_defence2.bin` — это ромхак, наш загрузчик его не принимает. Работаем с `rom/dune_usa.gen`.
Русский ROM часто лежит под именем «Dune - The Battle for Arrakis (USA).gen» (архив
`Dune_-_Battle_for_Arrakis_U_S_Rus_Shedevr_NewGame_Lipetsk_02_08_2011.zip`). Нужный файл: 1 МБ,
SHA-1 `7a7e3ec6aaeb3d8fbcfb779834565412252ce616`, по `$020D6B` — «НАЧАТЬ СНАЧАЛА» кодами шрифта
(`48 41 79 41 54 62 …`).

`web/src/rom/` раньше не попадал в git: правило `rom/` в `.gitignore` срабатывало на любой глубине.
Модули восстановлены 2026-10-17 по собранному JS опубликованной страницы, теперь в `.gitignore`

## Карта кода (`web/src`)

| Путь | Что там |
|---|---|
| `engine/` | Порт OpenDUNE (GPL-2.0) на TS с таблицами MD из ROM. Это вся механика. |
| `engine/core.ts` | Типы, глобальное состояние `G`, пулы юнитов, зданий, домов и команд, перечисления (`STRUCTURE`, `UNIT`, `ACTION`, `LST`, `SELECTION`). |
| `engine/tables.ts` | Таблицы PC (`tables.gen.ts`) и `applyRomTables(rom)` — замена их числами MD. Адреса: unitInfo `$06C5BC`, structureInfo `$06AFAE` (19×0x66), landscapeInfo `$06CCB6`, iconLandscape `$00581C`, анимации зданий. |
| `engine/game.ts` | Класс `Game`: загрузка миссии, `tick()`, команды игрока (`order`, `build`, `placeIt`, `place`, `cancelPlace`, `buildOptions`, `production`, `cheat`…). |
| `engine/unit.ts`, `structure.ts`, `house.ts`, `team.ts`, `map.ts`, `animation.ts`, `explosion.ts`, `script.ts`, `scriptfns.ts` | Порты одноимённых файлов OpenDUNE. Отличия MD помечены комментариями с адресами (`$00FECC` и т.п.). |
| `game/world.ts` | Адаптер движка для отрисовки: стабильные объекты `Unit`/`Structure`, `sync()` каждый кадр, сглаживание хода. |
| `gfx/` | Графика из ROM: `icons.ts` (клетки карты), `sprites.ts` (юниты, эффекты, порядок кусков спрайта как у VDP), `cursors.ts`, `pack.ts` + `zip.ts` + `skins.ts` (экспорт и импорт набора PNG для перерисовки). |
| `rom/dune.ts` | `DuneRom`: проверка ROM, адреса (`ROM = {...}`), VRAM спрайтов, кадры, картинки, карты миссий. `rom/lcw.ts` — распаковщик LCW, `rom/scenario.ts` — сценарии миссий. |
| `view/mapview.ts` | Отрисовка карты, курсор геймпада (разгон 1→3 пикселя за кадр, +1/16), C+стрелки — быстрая прокрутка (7, затем 14 пикселей за кадр), режим мыши, штриховка постановки, «OK» над двором. |
| `ui/command.ts` | Правое меню: приказы, производство, ремонт, улучшение, космопорт. Видно только в режиме мыши; с геймпада вместо него HUD оригинала и окно здания. |
| `ui/hud.ts` | HUD справа вверху, как на MD: кредиты цифрами ROM со счётчиком, картинка выбранного, полоса прочности, иконка заказа и вторая полоса (см. «HUD справа вверху»). |
| `ui/settings.ts` | Меню Start «НАСТРОЙКИ» и ввод пароля из графики ROM, пароли уровней и коды. |
| `ui/factory.ts` | Окна зданий с геймпада (постройка, заводы, космопорт, улучшение) как на MD. |
| `ui/intro.ts`, `ui/frontend.ts` | Заставка от включения, главное меню и выбор дома. |
| `gfx/mentat.ts`, `ui/mentat.ts` | Ментат: брифинг, советы, тексты победы и поражения, уход с картой. |
| `ui/endgame.ts`, `ui/score.ts`, `ui/finale.ts`, `ui/tutorial.ts` | Пролёт и картинка победы/поражения, итоги с паролем, финал с титрами, режим ОБУЧЕНИЕ. |
| `sound/` | Звук: драйвер GEMS из ROM на эмулированном Z80 + YM2612 + PSG в AudioWorklet (`sound.ts` — API игры). |
| `ui/assets.ts`, `ui/minimap.ts`, `ui/romstore.ts` | Просмотр ресурсов и набор PNG, радар, хранение ROM и скинов в IndexedDB (`dune-remaster` v2). |
| `main.ts` | Сборка всего: выбор ROM, миссии, кнопки геймпада (`padA`/`padB`, как в обработчике MD `$027B50`), мышь, автопостановка готового здания, HUD. |

## Инструменты разбора оригинала (`tools/`)

- `emu.py` — обёртка libretro Genesis Plus GX (`third_party/`, собирается `tools/build_emu.sh`).
  Сборка `gpgx_hook.so` даёт хуки CPU: `set_hook(e, fn)` с типами чтения, записи, исполнения и записи
  в VRAM. Ещё есть `e.vdp()` (VRAM, CRAM, регистры) и `e.ram()`.
  Раскладка кнопок проверена: `MD = dict(A="Y", B="B", C="A", START="START", ...)`.
- `play.py ROM OUTDIR "сценарий" --load st.bin --save st.bin` — сценарий из команд:
  `p A 3 10` (нажать на 3 кадра и подождать 10), `h DOWN 20` (держать), `w 60`, `s имя` (снимок),
  `sheet имя` (склейка снимков). Готовые сохранения: `out/emu_usa/st_hk1.bin` (миссия 1 Атрейдесов,
  курсор на дворе), `out/abtest/*.bin`, `out/screens/st_factory.bin`, `st_password.bin`.
- `trace_dma.py ROM STATE "сценарий" OUT.json` — все DMA и вызовы LCW за сценарий. Так находятся
  источники графики любого экрана.
- `m68kdis.py ROM START [LEN]` — дизассемблер 68000 (адреса в hex), нужен `pip install capstone`.
  Полный листинг ROM: `python3 tools/dis_full.py rom/dune_usa.gen > out/dis_full.txt` (вне git, ~370 тыс. строк).
  Искать в нём так: `awk '$1>="00FE60" && $1<="010000"' out/dis_full.txt`.
- В подготовленном снимке облачной среды уже есть ROM владельца `rom/dune_usa.gen`, обе сборки эмулятора
  и Python-окружение `/workspace/.dune-tools/venv` (Pillow, capstone). Сначала проверь их наличие;
  не удаляй и не скачивай заново. Если ресурсов нет, ROM владелец присылает вложением, эмулятор
  собирается `sh tools/build_emu.sh` (~1 мин), сохранения эмулятора делаются через `play.py`
  (от включения до миссии 1 Атрейдесов: Start, Start, A, A, A и так далее — см. «HUD справа вверху»).
- `render_plane.py ИМЯ БАЗА` — рисует плоскость VDP из дампа `out/screens/ИМЯ.vram/.json`.
- `lcw.py`, `vram2rom.py`, `vram2lcw.py` — распаковка LCW и поиск, откуда в ROM пришли тайлы VRAM.

## Что уже сверено с оригиналом

- **Кнопки** (обработчик `$027B50`, джойпад `$0EC0`, байты `$FFE41A`/`$FFE41B`):
  - A по своему юниту — выбор: курсор-прицел, 4 стрелки над юнитом;
  - A в точку — приказ, после него выбор снимается; A по тому же юниту — снять выбор;
  - A по своему зданию — выбор, ещё раз A — окно здания;
  - B — отмена; C+стрелки — быстрая прокрутка; Start — «НАСТРОЙКИ».
- **Постройка** (проверено в эмуляторе):
  - A по выбранному двору открывает полноэкранное окно (вкладки ВЫХОД/РЕМОНТ/СТОП, сетка иконок, картинка, название, цена/энергия/прочность);
  - выбор пункта запускает производство и возвращает на карту;
  - деньги списываются по 25 каждые 30 кадров (ветряк — 331 кадр, наш движок совпадает);
  - готовое здание **само садится на курсор** косой штриховкой: зелёная — можно, красная — нельзя; A ставит, дальше идёт короткая анимация стройки;
  - B отменяет постановку, над двором появляется «OK», A по двору снова даёт постановку;
  - A по своему зданию во время постановки открывает его окно.
- **Список двора** по коду MD `$00FECC`:
  - плиты 2×2 («ПЛИТЫ», 15 кредитов) доступны всегда;
  - тяжёлый завод и Дом IX со двора не строятся;
  - казармы WOR недоступны Ордосам;
  - бит 8 слова `$6` — «упёрлись в предел» (ставится в `$00DC60…$00DDF2` каждый тик, только у зданий игрока):
    двор — пул построек `$FFBEA2` пуст (70 мест на всех домах, плиты и стены мест не берут, таблица `$0204D4`);
    заводы юнитов и космопорт — пул наземных юнитов (номера 25–101, флаг `$FFC72C`) или предел дома;
    высокие технологии — нет места для авиации (номера 0–10, `$FFC728`); дворец Атрейдесов — пул наземных.
    У двора при бите 8 в списке только плиты и стены (`d3 &= 0x4002`). Сделано: `structureLimitReached`;
  - второй дворец и второй космопорт не строятся: `$FF7C9C` + дом·$20 — счётчики зданий по типам (+2 дворец,
    +$0B космопорт), растут уже при создании строящегося здания (`$00E5CE`). Сделано, тест `tools/sim/build_limits.ts`.
- Танк и осадный танк собираются из двух кусков (башня — первый кусок, лежит сверху). Таблицы
  `$2EC7A` и `$2F2FA` (8 корпусов × 8 башен × 26 байт), кадры отдачи — `$2F97A` и `$2FFFA` (та же раскладка).
- **Отдача танков** (сделано по коду, в эмуляторе не сверялось): `Unit_Fire` ($044B38) при выстреле пулей
  у типов 9/10 ставит кадр отдачи и бит 6 в `$7(unit)` (`Unit.recoil`). Обновление спрайта `$012210`
  не трогает башню, пока бит стоит. Бит снимают ветки цикла юнитов `$04378C`: тик поворота ($043A9C)
  и тик наведения башни ($0439BA), каждая сначала перерисовывает, потом сбрасывает. Обычный кадр
  возвращается при следующей перерисовке (`unitSpriteUpdate`): поворот, шаг или следующий тик поворота.
  Итог — 3–4 кадра. Проверка: `node --experimental-transform-types tools/sim/tank_recoil.ts`.
- **Тик поворота MD — каждые 2 кадра** (`$0437C8`, у PC `adjustToGameSpeed(4,2,8)` = 4). Исправлено.
  Таймеры цикла юнитов MD: движение +3, поворот +2, наведение +20, скрипт +5, анимация +5, отклонение +60;
  счётчик `$FFC598` растёт в VBlank ($00B550), как наш `timerGame`.
- **Не сверено:** `Unit_MovementTick` MD ($047FC2) у пехоты и гусеничных сначала доворачивает корпус
  ($047E9C) и только потом едет — у нас движение из OpenDUNE.
- **Значки над зданиями игрока** — процедура `$00DC9C` (по типу здания, таблица переходов `$DC88`):
  - двор: «OK», если заказ готов (бит 13 слова `$6`) и двор не выбран (бит 15, `$FFC578`), иначе
    молоток при ремонте (бит 13 слова `$4`); индекс 3 — центр 2×2, смещение (20, 20);
  - дворец: «OK», если `$56` = 0 и не ждёт цели ракета (`$FFDC4C`), иначе молоток; индекс 6 — (36, 36).
    Бит 8 слова `$6` в этом условии не опознан, не учитывается;
  - описания: «OK» — таблица `$009ABA`, молоток — `$0659FE`; тайлы уже в VRAM спрайтов (кадры 24 и 26);
  - флаги значков — байт `$FFC868` + номер здания: бит 1 «OK» (`$009A66`), бит 0 молния (`$009ADA`), бит 2 молоток
    (`$009B2A`); `$009A32/36/3A` их снимают (это не «знак запрета», как считалось раньше);
  - молния над ветряком (`$00DD6A`, описание `$0658E8`): потребление дома больше выработки. Бит 1 слова `$4`
    в условии стоит у всех поставленных зданий (у ветряка `$4` = 7, у двора `$1003`);
  - значки мигают силами спрайта (`$0010B0`: байт +4 — счётчик, +5 — перезагрузка, бит 5 байта +7 — мигание):
    «OK» 6 кадров виден / 1 скрыт, молоток 7/1, молния 3/1 (замерено для «OK» в эмуляторе).
- **HUD справа вверху** (`ui/hud.ts`, сверено в эмуляторе побайтно, тесты `tools/sim/hud_bars.ts` и `tools/browser/hud.mjs`):
  - выбор, что показать, — `$0294C2` (каждый кадр карты). Здание `$FFC578` берётся, только если не выбран юнит `$FFC25C`
    и стоит бит 15 слова `$6`; чужое здание или юнит — только картинка и прочность;
  - спрайты (описания `$06A798…$06A80E`, координаты экрана): кредиты 6 тайлов с (256, 16), картинка 4×3 (272, 48),
    прочность 4×1 (272, 72), иконка заказа 4×3 (272, 88), вторая полоса 4×1 (272, 112) или (272, 80);
  - картинка `$0098E0` и иконка `$009946`: кадр из таблицы `$060E8C` (+$14 описания здания `$06B954` или юнита
    `$06C5BC`), байт +4 кадра: FE — строка палитры 1, FF — строка 3, остальное не рисуется;
  - полосы рисует `$009772` в тайлы: строки 2 и 7 — рамка цвета 12, 3–6 — заливка, длина
    min(v, max)·32/max (без остатка −1). Прочность `$0096CA`: цвет по занятому тайлу 4/2/2/6 (`$009742`);
    вторая полоса `$009866`: цвет 7 (синий) или 3;
  - вторая полоса: стройка — время стройки − (countDown>>8), пока идёт (бит 14 `$6`, снимается в `$0121CA`);
    улучшение — иконка `$40` и 100 − `$55`; ветряк — потребление/выработка дома (`$1C`/`$1A`) на y=80;
    завод пряности и хранилище — кредиты/вместимость, оба ÷2, пока вместимость > `$7FF`, цвет 3;
    космопорт — доставка; дворец — иконка спецоружия (у Атрейдесов фримены `$5E`); харвестер — груз из 100, цвет 3;
  - кредиты `$00A5DA`: строка `%6d`, тайл цифры = `$050AD4` + (символ − 0x2F)·32; счётчик `$011F38` догоняет
    кредиты дома, как в коде (сдвиг ÷4, не больше 128, копится по 1/8), в начале миссии считает с нуля;
  - знак запрета 3×3 поверх иконки заказа (тайлы `$065A1A`, строка 0, в (276, 88)): двор — бит 8 и заказ не плиты
    и не стены; другие (кроме космопорта) — бит 8, высокие технологии — ещё и без места для авиации;
  - «НЕТ ДЕНЕГ» (`$0099AC`, тайлы `$065B4E`, 11 в строку, в (112, 112)): пока досчитанное < 50; при изменении —
    взвод, когда досчитало — 90 кадров показа, потом пауза 900 и показ по 60. Сверено в эмуляторе (кредиты
    записаны в RAM). Счётчик и в оригинале останавливается на 41 при 40 кредитах;
  - **полоса ремонта сделана:** `$048926` сохраняет начальное время ремонта в `$5A` юнита
    (`Unit.repairTime`), `$02976C` вычитает остаток `$56` здания. Синяя полоса под иконкой ремонтируемого
    юнита, y=112. Проверено вызовом `$04880A` в Genesis Plus GX: трицикл с HP 50/99/100/1 получает
    начальное время 320/5/1/632. Тест `tools/sim/hud_repair.ts` проверяет ход, завершение, выход и сброс;
  - **щелчки счётчика сделаны:** `$012118` вызывает звук 0x34 (приход) или 0x35 (расход) каждый четвёртый
    шаг счётчика; на неподвижном числе щелчков нет. Фаза `$FFD6B4` сохраняется между миссиями.
    Проверено хуком `$00A7DC` в эмуляторе для 990→965 и 965→990; тест `tools/sim/hud_bars.ts`;
  - **A по картинке не подтверждено:** `$00A5B0` проверяет рамку x=272…303, y=48…71, но прямых вызовов,
    PC-relative вызовов или указателей на эту функцию в этом ROM не найдено. При A над картинкой
    выбранного двора хук не фиксирует её вызов и окно здания не открывается. Новое действие не добавлено;
    прежний пункт плана был предположением, его надо дополнительно исследовать, если это поведение нужно.
- **Числа домов MD** (таблица `$06C75C`, 30 байт на дом, раскладка PC без имени) подставляются из ROM.
  Отличается время спецоружия (`+$0A`): Харконнены 400, Атрейдесы 50, Ордосы 125 (у PC 600/300/300).
  Износ в таблице на 1 меньше, MD прибавляет 1 при ударе (`$00BEB2`), итог как у PC.
- **Дворец MD** (`$00BDEA`, тик дворца раз в 60 кадров, как у PC): после спецоружия пауза `$4E` в тиках дворца —
  ракета 300 (`$022D98`), фримены 180 (`$02301C`), диверсант 240 (`$0230B4`); пока она идёт, отсчёт `$56` стоит
  и в HUD знак запрета; отсчёт стоит и при бите 8. В движке — поле `Structure.specialWait`.
  Не перенесено: у Ордосов при `$56` = 0 код зовёт `$043224` (создание юнита 6) и `$047072` — смысл не разобран.
- Кадры с источником `0x7F……` в таблице `$060E8C` — сырые тайлы, которые игра шлёт DMA в VRAM;
  кадры 88–106 — иконки меню постройки (`$0098E0`, VRAM `$F280`).
- Звуковая волна: кадр по 16 направлениям из таблицы `$06C6CC` (код `$0124AC`).
- Анимации зданий: у иконок MD только 3 кадра (0 — стройка, 1 — развалины, 2 — готово). Кадры
  дальше рисуются как кадр 2.

## Сетевая игра, этап 1 (2026-10-19): lockstep на картах ROM, до 6 игроков

Схема: каждый клиент считает игру сам, по сети ходят только команды. Сервер `server/dune-net.mjs` (Node + `ws`)
раз в 100 мс рассылает ход — команды всех игроков за это время; ход n выполняется в кадр n×6 до такта движка.
Состояние сверяется контрольной суммой (`Game.netHash`) каждые 50 ходов, расхождение — сообщение у всех.

| Что | Где |
|---|---|
| Несколько людей в движке | `engine/core.ts`: `G.net` (маска людей, команды), `isHuman`, `isLocal`, `humanHouses`, `creditsNoSilo`; `house.ts`: `houseAreAllied` по командам, `houseAlliedToHuman` |
| Матч, команды, сверка | `engine/game.ts`: `loadNetwork`, `netSpawns`, `execNet` (`NetCommand`), `netHash`, `netLevelEnd`, `netQuiet`, `netStarportPrice` |
| Клиент | `net/session.ts` (`NetSession`: комнаты, ходы, `advance`), `net/controls.ts` (`installNetControls`) |
| Лобби | `ui/network.ts`: серверный режим — `openServer`, `setServerRooms`, `setRoom`; карты ROM — `romMapList` в `main.ts` |
| Запуск и цикл | `main.ts`: `startNetMatch`, `onNetEnd`, `leaveNetMatch`, `net.advance` в `view.onFrame`; `game/world.ts`: `loadNetwork` |
| Сервер | `server/`: `dune-net.mjs`, тест `test/dune-net.test.mjs`, `Dockerfile`, `compose.yml`, `Caddyfile.dune`, `deploy-vps.ps1` |

Правила (иначе игры у игроков разойдутся):
- в кампании `isHuman(h)` ≡ `h === G.playerHouseID` — её поведение не меняется (проверено побитово, см. проверки);
- в сети `G.playerHouseID` — только местный зритель: звуки, сообщения, экран. В симуляции — `isHuman`, `humanHouses`;
- интерфейс не меняет движок: на время матча методы `Game` (`order`, `build`, `place`…) подменяются отправкой команд,
  а `execNet` вызывает методы класса (`Game.prototype.order.call`), иначе команда уходит в сеть по кругу;
- интерфейсное состояние (`G.selectionType`, `G.unitActive`, «призрак» постановки) симуляция не читает; списки заказов
  в сети считаются без следа (`netQuiet`), цены космопорта — из зерна матча, не из общего генератора;
- скрипты в сети не замедляются вне экрана; выбор юнита не трогает карту (`unitSelect`).

Матч: карта ROM 1..27, двор + 2 квадроцикла + кредиты (1–50 тыс.), стартовые точки — по зерну, команды как можно
дальше. Дом — он же игрок и фракция: в комнате дома не повторяются (Атрейдесы, Харконнены, Ордосы, Фримены,
Сардаукары, Наёмники). Победа — последняя команда со зданиями или боевыми юнитами; игра у остальных идёт дальше.

Ограничения этапа 1: тумана войны нет (вся карта открыта; с 2026-10-20 туман по домам есть — см. «Туман по домам»); ИИ нет; лазерный танк, дрон и площадка дронов
запрещены (их код использует sin/cos/hypot — не гарантирует одинаковый результат в разных браузерах); пулы
движка общие — 102 юнита и 79 зданий на всех; переподключения нет (вышедший игрок остаётся без управления);
паузы нет; наблюдатель получает журнал ходов и догоняет игру.

### Текущий этап: дворцы, независимые готовые заказы и автоматическая постановка (2026-10-19)

Владелец поручил этап 2 (большие карты / 4×4 / лимиты), затем добавил приоритетные исправления дворцов и очереди.
**Большие карты и 8 игроков пока не реализованы.** Исследованы ограничения: не только 64×64 и 6 домов, но и
16-битное кодирование целей EMC, знаковые расстояния, singleton-слоты плит/стен, массивы вида и ROM-таблицы
смещений. Нужен отдельный завершённый этап миграции с сохранением контрольных сумм кампании; не увеличивать
одни константы без замены упаковки и зависимостей. Существующие JSON/PNG карт пока остаются предпросмотром.

Реализовано в текущей рабочей папке:
- `structureActivateSpecial`: вызванные Фримены принадлежат владельцу дворца, а не отдельному дому FREMEN.
  Человек получает их и диверсанта на охране, может сразу отдавать приказы; AI продолжает HUNT/SABOTAGE.
- `Structure.readyBuildings` хранит `{type,cost}` готовых зданий, `readyUnits` — индексы готовой техники;
  производство сразу освобождается для следующего оплаченного заказа. Готовые здания не занимают пул;
  плиты/стены используют отдельный призрак, чтобы singleton-слоты ROM не перезаписывали его при новой стройке.
- Размещение выбирается по типу из готового запаса, отмена возвращает его в запас; ПКМ отменяет заказ с возвратом.
  В меню мыши и геймпада учитываются готовые количества. Ограничение дворца/космопорта распространяется и на запас.
- У выбранного строительного двора завершение автоматически включает площадку на курсоре; после установки
  подхватывается следующая готовая. Отмена не уничтожает готовую постройку. Стройка продолжается во время размещения.
- Закрытый выезд не останавливает выпуск: техника ждёт отдельно. Транспортник забирает готовую технику из запаса,
  не трогая текущий незавершённый заказ; при открытии выезда техника выпускается обычным способом.
- Сетевые `place` содержат необязательный `t` (тип готового здания), `unreadyB` отменяет готовое здание.
  `netHash` учитывает очереди и готовый запас. Внутри execNet не вызывать подменённые UI-методы: использовать
  `Game.prototype.*.call`, иначе отмена повторно отправит команду или зациклит stopAll.

## Исправление зацикливания звука и пропадающей музыки (2026-10-18)

Владелец уточнил: «зацикливание и местами нет вообще музыки». Установлена главная причина:
`SoundMachine` всегда загружал банки заставки, а не игровой набор. `$02DCF0` / `$02DD04` задаёт
`{ patches: $0D02AE, envelopes: $0D0251, sequences: $0CF970, samples: $0C8160 }` — всего 13 секвенций.
`$02DCA0` / `$02DCB8` задаёт `{ patches: $0FE2B6, envelopes: $0FE185, sequences: $0F6363, samples: $0D06BF }`
— 84 секвенции. Запуск игрового курсора `$19` в первом наборе читал чужие данные как команды
секвенсора, отключал таймер YM и блокировал новые звуки/STOP_ALL. Это воспроизводилось без браузера.

В оригинале `$01744A` включает банк заставки; `$017A0C` после выхода из её главного меню и `$030686`
перед обучением — игровой. Теперь `Sound.useBank()` передаёт выбор в AudioWorklet и заново
создаёт звуковую машину (оригинал тоже перегружает драйвер через `$001624`). Заставка и главное меню
используют `intro`, настройки/выбор дома/обучение/миссии — `game`. Возврат в главное меню восстанавливает
`intro`. По умолчанию у `SoundMachine` игровой банк; для отдельного рендера заставки:
`BANK=intro node --experimental-transform-types tools/sim/sound_render.ts 0 10 out/intro.wav`.
Без `BANK=intro` последовательности относятся к игре. Убран обходной START 0 / STOP 0 при прогреве:
правильный банк запускает эффекты и без него. Неверные номера секвенций игнорируются до подачи в Z80.

Также восстановлена смена боевой музыки в основном цикле `$01253E…$01255C`, ранее она происходила
только при закрытии окна. Пять боевых номеров 8…12 выбираются без повтора предыдущего, длительности
берутся из ROM. Фонотека ROM содержит 18 пунктов, саундтрек не ограничен четырьмя мелодиями.

Музыкальная секвенция 0 теперь допустима и хранится отдельно от отсутствия музыки (`null`).
`playMusicSequence()` учитывает заставку и обучение; `previewMusic()`/`endPreview()` — фонотеку.
Выключение/включение сохраняет выбранную мелодию, эффекты можно выключить независимо, а закрытие
настроек возвращает нужную музыку. До запуска AudioContext короткие эффекты старше 250 мс отбрасываются,
после разрешения звука стартует актуальная музыка. Смена банка очищает команды прежнего экрана.

Проверки: `node --experimental-transform-types tools/sim/sound_recovery.ts` — холодный SFX $19,
240 команд START/STOP, новая музыка после них, STOP_ALL, повторный запуск, банк заставки и неверный номер.
`node tools/browser/sound_recovery.mjs rom/dune_usa.gen` — настоящий AudioWorklet и измерение сигнала:
заставка, банк настроек, SFX, фонотека, выключение/возврат, выбор дома, смена боевой мелодии и независимые
настройки, без processorerror. `GAME_URL` задаёт другой адрес, проверен также одиночный HTML на 4180.
Пройдены сборка, npm-тесты, `menu_sounds.mjs` и `frontend_hd.mjs`. Временные WAV/трассы в `out/audio-fix/`
в Git не добавлять. Известное расхождение огибающих YM2612 с GPGX остаётся отдельной задачей.

### Вражеский перевозчик с харвестером кружит без базы (замечание владельца, 2026-10-19)

Наблюдение: перевозчик врага с харвестером кружил на месте, пока к нему не подвели технику, потом сбросил
только харвестер; здания врага были уничтожены. Разбор (`tools/sim/emc_unit_dump.ts`, `carryall_no_refinery.ts`):
- скрипт перевозчика в ROM (тип 0, начало 1743, ветка «груз есть, цели нет» — 1838): если груз — харвестер со
  спайсом (`unitGetAmount` ≠ 0), то 3 круга (подпрограмма 1099–1128: скорость 200, курс +10, пауза 25) и поиск
  завода `unitMoveToStructure(12)`; завода нет — снова круги, бесконечно. Пустой харвестер или другой груз —
  `unitTransportDeliver` на месте. Значит, кружение без заводов — поведение оригинала MD, не ошибка порта;
- `unitMoveToStructure` сначала берёт здание по `originEncoded` харвестера без проверки типа и дома (как в
  OpenDUNE): если номер уничтоженного завода займёт новое здание, перевозчик полетит к нему;
- сброс «когда подвели технику» в симуляции не воспроизвёлся (юниты игрока рядом сброс не вызывают). Не выяснено.
**Решение владельца — «надо чтоб сбросил и улетел» (сделано):** `scriptfns.ts` → `unitGetAmount` отвечает «пуст»,
если перевозчик везёт харвестер, а у дома нет ни одного завода очистки (`houseHasRefinery`): скрипт ROM сам идёт
в ветку сброса $1859. После сброса `unitTransportDeliver` ставит `Unit.carryallLeaving`, и `unit.ts` →
`unitCarryallLeaveTick` уводит перевозчик к ближайшему краю карты и убирает его (скрипт он больше не исполняет).
Действует для всех домов. Это отступление от MD по просьбе владельца. Проверка: `tools/sim/carryall_no_refinery.ts A 4`
(3 круга, сброс около 500-го кадра, «перевозчик улетел за край» около 650-го).

### Линии до цели, как в Red Alert (просьба владельца, 2026-10-19)

Как в OpenRA (`DrawLineToTarget`): от каждого юнита отдельно — линия к тому, во что он будет стрелять
(малиновая `DC143C`, как `TargetLineColor` OpenRA), или куда едет (зелёная), с отметками на концах.
- `gfx/target-lines.ts`: `unitTargetLine` берёт цель из движка (`targetAttack`, иначе `targetMove` у движущихся);
  юнит-цель — по живой позиции, здание — по центру; `drawTargetLines` не рисует линию к клетке в тумане
  (иначе выдала бы врага);
- `view/mapview.ts`: у выбранных своих — всё время; `flashOrders` — после приказа 2,4 с в любом случае, дальше
  линия держится, пока цель та же (`orderLines`, ключ targetAttack:targetMove), то есть до новой цели или места,
  уничтожения цели или прибытия — «не сбрасывать указание, пока не переведу»;
- `main.ts`: `view.flashOrders` после каждого приказа (щелчок мыши, прицел, A геймпада — там выбор по оригиналу
  снимается, а линии остаются).
Только чтение состояния — в сети одинаково и ничего не меняет. Проверено в браузере (H4, открытая карта).

### Туман по домам в сети (2026-10-20)

Раньше в сети вся карта была открыта и общая. Теперь у каждого человека свой туман: игрок видит только то, что разведал сам
(союзник по команде тоже не делится). Кампания побитно прежняя.
- `engine/core.ts`: `Tile.unveiledHouses` — маска домов, раскрывших клетку; `NetGame.view` — чей туман на экране
  (`1 << local`, у наблюдателя — все люди). Симуляция `view` не читает.
- `engine/map.ts`: `mapUnveilTile(packed, дом)` в сети ставит бит дома и не трогает общий слой; `tileRemoveFogInRadius(t, r, дом)`
  (по умолчанию `G.playerHouseID` — так в кампании); проверки `mapIsUnveiledFor(packed, дом)`, `mapIsUnveiledByAnyHuman`,
  `mapIsUnveiledLocal` (только для интерфейса). В кампании все три сводятся к прежним `mapIsPositionUnveiled`/`isUnveiled`.
- Почему общий слой открыт: от `isUnveiled` и иконок тумана в `overlayTileID` зависят стены, кратеры, тип ландшафта.
  В сети они остаются как на этапе 1 (`isUnveiled = true`, без иконок тумана); края тумана местного игрока строит
  `World.netFog` по маске, как `Map_UnveilTile_Neighbour` (иконки группы 7). Отрисовка, `FogOfWar`, мини-карта, линии до цели,
  частицы и выбор здания читают `world.map.overlay/unveiled` — поэтому работают по маске местного игрока без отдельных правок.
- По домам в сети (вместо `G.playerHouseID`, иначе игры разойдутся): туман снимают юниты, здания, дроны — для своего дома;
  выстрел, который дом не видел, снимает туман радиусом 2 вокруг стрелка у каждого такого человека (как в оригинале у игрока);
  `unitUpdateMap` и выход из здания — кто из людей видит юнит, по маске каждого (`unitHouseUnitCountRemoveFor`);
  воздушная цель человека в его тумане не берётся (`unitGetTargetUnitPriority`); червь — по клеткам, раскрытым хоть одним человеком.
  `prepare()` в сети не раскрывает «уже открытые» клетки (иначе всё открылось бы местному игроку).
- Интерфейс: `Game.isVisible/visibleUnits/selectAt/defaultAction` и вспышки взрывов в `main.ts` — по `mapIsUnveiledLocal`;
  щелчок по чужому двору в тумане даёт «ехать», а не «атаковать».
- `netHash` учитывает маски; `tools/sim/net_determinism.ts` в хеш кампании теперь добавляет туман (`isUnveiled`, `overlayTileID`,
  маску) — старый движок считается тем же хешем.
- ИИ в сети (`net-ai.ts`, другая сессия): маски у компьютеров нет, `mapUnveilTile` для не-человека — `false`; юниты людей
  у всех `seenByHouses = 0xff`, как в оригинале, поэтому ИИ видит людей.

Проверки: `campaign A/O/H, миссии 1 2 4 6 9, 6000 кадров` — все хеши (с туманом) совпали со старым движком;
`net 1 0 5 6000` и `net 0 1 5 6000` — 100 сверок совпали; `web/test/net-fog.test.ts` — маски, экран, наблюдатель, одинаковые
хеши и маски у местных 1, 0 и наблюдателя; web 17/17, server 4/4, tsc без ошибок. В браузере (сборка, два клиента через
локальный сервер): 18 сверок хешей на кадрах 300…5400 совпали; у Атрейдесов после разведки на экране 303 клетки = их маска,
база Харконненов видна, у Харконненов — только свои 35 клеток, разведчика видно лишь в их раскрытой зоне.
Не проверено: туман у наблюдателя в браузере (только тест), звуки боя в тумане (по-прежнему слышны всем).

### «Юниты едут в упор, потом стреляют» — разбор и групповая атака (замечание владельца, 2026-10-20)

Разбор (`tools/sim/attack_range.ts ТИП N КАДРОВ group|each unit|ЗДАНИЕ`, `tools/sim/emc_unit_dump.ts 0 247`):
- атаку ведёт скрипт ROM (общий скрипт наземных, `ACTION.ATTACK` → адрес 83): `unitFire`; цель дальше
  `fireDistance` — `unitCalculateRoute` к цели; ближе — `unitRotate` (довернуть). Маршрут шагает по клеткам только
  через `unitCalculateRoute`, поэтому юнит встаёт в центре первой клетки в пределах дальности. Расстояние — как в
  OpenDUNE (`objectGetDistanceToEncoded`, у здания до ближней клетки края). В движении (`ACTION.MOVE`, адрес 640)
  скрипт тоже ищет цель и стреляет на ходу;
- замеры по одиночке совпадают со скриптом: танк (дальность 4) стреляет с 3,2, осадный (5) — с 4,5, квадроцикл (3) —
  с 2,2, ракетная установка (9) — с 8,25; по зданиям встают в 3–4 клетках от края. Вплотную в чистом поле никто не
  подъезжает. Толпой (рамкой — в MD её нет) все едут к клетке цели, задние упираются и объезжают, один из шести
  танков не выстрелил вовсе.
- **Сделано (отступление для группового приказа, одиночный не меняется):** `Game.orderGroup` (рамка, щелчок по цели,
  `targetClick(packed, others)`, в сети — одна команда `order` на всю группу, по 64 юнита) → `scriptfns.ts`
  `unitsAssignAttackSpots`: каждому, кто ещё не достаёт, — своя ближайшая свободная проходимая клетка, откуда цель в
  пределах дальности, без своих зданий на линии огня (ближние к цели выбирают первыми); `unitCalculateRoute` везёт
  туда вместо клетки цели (`Unit.attackSpot`), занятую подменяет, пути нет — как в ROM, к цели. Стрельбой управляет
  тот же скрипт. Итог в симуляции: толпой стреляют все шесть и раньше; кампания H4 A1 O7 побитно как раньше, сеть —
  хеши совпадают, `net_ai.ts`, web 17/17.
- Не выяснено, что именно владелец видел «в упор»: в замерах этого нет. Нужен пример (какие юниты, приказ щелчком
  по врагу или в точку рядом, против юнитов или зданий).

### Червь, спайс под огнём, следование, атака своего, приказы толпой (замечания владельца, 2026-10-20)

- **Червь под юнитами** (`view/mapview.ts`): червь и его пасть (взрыв 13, `drawWormMouths`) рисуются в самом нижнем
  слое наземных, юниты над ним; раньше порядок был «по y», и червь ниже юнита закрывал его.
- **Спайс исчезает от взрывов и выработки** (`map.ts` → `mapChangeSpiceAmount`). В PC под спайсом в `mapTileID` лежит
  песок; в картах MD спайс нарисован в самой клетке, и «вернуть исходную клетку» возвращало спайс — взрывы и харвестеры
  его не убавляли до песка. Теперь, если исходная клетка сама спайс, кладётся песок ландшафта (`landscapeIcon(0)` = 127).
  Взрыв по-прежнему только в раскрытой клетке без тумана (как `Explosion_Func_TileDamage`). Проверка
  `tools/sim/spice_crater.ts`; в браузере (A2) квадрат 3×3 в поле стал песком на экране. Кампания H4/A1/O7 за 6000
  кадров побитно прежняя (до песка за это время не вырабатывается), но в длинной игре экономика теперь как в MD.
- **Места цветения** уже работали как в оригинале: выстрел (`funcTileDamage`) или наезд (`unitMove` → `mapBloomExplodeSpice`,
  юнит пропадает) открывают поле. Проверка `tools/sim/spice_bloom_shot.ts` (A2: 162 → 197 → 252 клеток спайса). В сетевых
  картах мест цветения нет (они из сценариев кампании).
- **Следование** (`main.ts` → `padA`): как в MD, A по своему юниту при выбранных — приказ «двигаться» на его клетку;
  `unitSetDestination` (как OpenDUNE) делает из неё цель-юнит, выбранный едет за ним и встаёт рядом. Мышью левая кнопка
  по своему юниту по-прежнему выбирает его (как в Red Alert); следовать — кнопкой «Движение». `tools/sim/follow_unit.ts`.
- **Атака своего здания** (`scriptfns.ts` → `friendlyStructureOnRay(..., target)`): приказ «Атака» по своему зданию
  повреждает его, как в MD; раньше добавка «своё здание на линии огня закрывает выстрел» блокировала и само здание-цель.
  Остальные свои здания на линии огня по-прежнему закрывают. `tools/sim/own_building_attack.ts`.
- **Движение и патруль толпой** (`Game.orderGroup` → `Game.spreadPoints`): в пустую клетку каждый получает свою клетку
  рядом, смещение от центра группы сохраняется и сжимается до ~√N (не больше 3); раньше все ехали в одну клетку и
  толкались. Приказ на клетку с объектом (следование, вход в здание) не раскладывается. Атака толпой — своя клетка на
  дальности огня, у каждого по его дальности (см. «Юниты едут в упор»). `tools/sim/group_orders.ts`.
Проверки: все симуляции выше, `net_determinism` net — хеши совпадают, web 17/17, tsc.
